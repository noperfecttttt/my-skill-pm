# 终审电池：宣告"定稿 / 一致 / 可提交"之前必须跑完

> **触发时机**（任一动作之前，一步不跑不得宣告）：
> - 宣称"需求文档定稿 / 与原型一致 / 内部无矛盾 / 可以提交"
> - 推进状态到 ready / prototyped / done
> - 执行提交
>
> **为什么要有它**：增量修订只改被点名处，而「完成」的判定标准会悄悄退化成
> **"我手头那处改完了"**，不等于全文一致。
> 实战里出现过连续 5 轮追问（"一一核对了吗" → "确定没问题吗" → "全文都读了吗"），
> **每一轮 AI 都已宣告"核对完成"，每一轮追问后都挖出真实矛盾。**

---

## 终审五步（逐步留证据）

### 1. 全文逐节通读——不是只读本轮改的章节

**摘要 / 派生层必须逐字核**：概览、角色与概念、规则汇总、验收标准、流程图。
它们最容易停在旧版本。

> 实证：概览里的模型比正文落后 **7 个小版本**仍无人发现——因为没人会回头读概览。

### 2. grep 不变量电池

把本需求生命周期中**每一次被推翻的旧设计 / 旧术语 / 旧选项**维护成清单，逐词 grep，
**除变更记录外必须为 0**。

清单怎么来：**每做一次演进决策，随手往里加旧词**——这是终审能收敛的前提。
（如：星级 / 保存草稿 / 两个开关 / 仅导师 / 待原型回填）

### 3. 需求 ↔ 原型双向核对

1. 先拿原型校需求（补漏 / 订正过时）；
2. 再拿真实页 + 另一端校原型（端间漂移：某端漏块、路由名不同）。

关键事实用 grep 客观验证（控件出现次数、选项集、被删项 = 0），**不靠印象**。

### 4. 引用完整性

文中引用的每个编号 / 章节指针都有定义、编号连续无悬空。

> 实证：某规则被引用但汇总表里没有定义；另一条与正文互相矛盾——都是 grep 一次就能发现的。

### 5. 摘要层逐条对照

概览的每一条（一句话 / 改动页面 / 核心规则 / 本期不做）逐条对到正文与原型。
**路由 / 入口必须含双端差异**（另一端的名字可能不同）。

## 签核账本要自己对账

**为什么单列**：验收走查的三个视角读的是需求正文、页面规格、原型——
**签核账本自己不在材料里**，所以覆盖账本漏登记，三视角一条都报不出来，
要等状态推进时才暴露，那时已经是最贵的时刻。

刷新签核时**必须自己跑一遍对账**：

1. 需求正文 + 各页规格里的**规则编号 / 验收编号全集** → 逐个在账本里找得到
   （含明确停用的编号，写「不启用」也算对账）；
2. 每张规格「字段清单」第一列的字段名 → 逐字在字段账本里找得到（**逐字一致，不同义改写**）；
3. 账本里的**旧版本残留**：本轮被推翻的叫法在账本里同样要清干净——
   **账本是上个版本写的，它不会自己跟**；
4. 改完先**空跑一次状态推进检查**再宣告。

> 实证：一次刷新同时查出 3 条规则、3 条验收、3 个字段全部漏登，都是前两轮版本新增的。

## 影响面的两个高频盲区

### 1. 带导入 / 导出的业务，任何模型层改动都要双向过一遍

**导入 / 导出是业务数据模型的一个投影面。**

触发面**不只是"字段自定义"**：新增或改枚举、改字段类型、加删实体、改层级关系、
加校验规则、改字段权限可见范围——**任何改变"被序列化的那份数据"的调整都算**。

| 侧 | 至少覆盖 |
|---|---|
| **导入** | 导入模板文件、字段映射、**模板匹配校验**、必填/枚举校验、大小与并发限制 |
| **导出** | 导出列结构、单元格内容、汇总表的列并集对齐、跨端一致 |

每一项写清"是否波及、怎么改、若不改的理由"。理由必须是"数据上确实不相干"，不能是"没想到"。

> **导入往往比导出更硬**：导出漏字段只是内容不全，**导入模板不匹配是直接报错、数据进不来**，
> 反而最容易在"本期不做导入导出"里被一并忽略。

**"不做导入导出功能" ≠ "改动不连带到导入导出"**——前者是范围决策，后者是数据耦合事实。

**判据用数据实体的消费下游，不是功能名匹配**：以被改的**数据实体**为起点，
拉出它的全部消费下游（导入 / 导出 / 端渲染 / 详情 / 统计 / 推送），导入导出只是其中必查的两支。

### 2. 同名动作要逐承载位核

见 `evidence.md §七`——"此页没有 X"是负面结论，须穷尽承载位才能下。

## 呈现细节：沿用平台既有做法，禁自造一套

**呈现细节** = 多值分隔符 · 空值显示什么 · 时间/数字/金额格式 · 文件名与编码 ·
表头结构 · 超长截断 · 默认排序 · 提示语措辞。

这些平台其他同类功能早有一套。**写死一个"看着合理"的值 = 让研发在同一个产品里长出第二套**，
对方一眼就能看出来。

- 默认写「**沿用平台既有做法**」，不给具体值。
- 要写具体值必须有信源三选一：① 同类功能的既有实现 ② 设计规范或字典 ③ 对方明说。
  **三者都拿不到 → 写「沿用既有 X」并注明由研发照现行实现走，不编默认值。**
- **禁逐项断言「必有值 / 必填 / 一定不为空」**，除非有实证。
  看起来"总该有"的字段都可能为空；**写错一格，研发就照着省掉一个空值分支。**
- 通则写一次置于表前，并声明"与下文任何格式描述冲突时以平台既有实现为准"。

**自查 grep**：`、` `;` `｜` 出现在"多个…用…拼接"句式；`yyyy` `HH:mm` `.xlsx` `UTF-8`；
`{业务名}_{内容}_{时间戳}`；`必有值` `必填` `一定` `不会为空`。

**一句判据**：这个值，我是从平台哪里看来的？**说不出来源 = 自造，改掉。**

### 姐妹条：要在规格里"写死"某个算法或阈值，先查共用组件是否已硬编码

这一格特别容易踩，因为这类校验往往**不在页面配置里，而在共用前端组件里**——
查配置查不到，很容易读成"没人实现过、由需求侧定"。而组件是全平台共用，
规格一旦写反就只剩"改规格 / 改影响面巨大的组件"两条路。

**顺序**：① 先查共用组件有没有现成实现 → ② 有就照它写，并标「平台既有能力、本单不实现」
→ ③ 觉得不合理另立一条给平台的改进建议（不阻塞本单）→ ④ 真要改共用组件，那是独立需求。

> **错的不是"写死"这个动作（消歧是对的），是写死之前没查。**

## 只写现状，不写过程

需求正文**全文只描述产品现状**（现在时）。禁止出现过程 / 决策 / 演进叙述：

| 禁写 | 举例 |
|---|---|
| 决策归属与时间 | "PM 拍板"、"某某确认"、"经确认" |
| 方案演进 / 否定 | "曾定 X 现改 Y"、"推翻上一版"、"改回"、"（视觉锁定态，拍板）" |
| 版本对比 | "v1.2 曾…v1.3 改回"、"原 BR-10 是…现…" |
| 作废旧词表 | 这类过程留痕去流水账 |

- ❌ "复选框锁定态由「已勾选」改回「取消勾选+置灰」（推翻 v1.2，拍板）"
- ✅ "总开关开启 → 复选框取消勾选 + 置灰锁定不可改"

**过程 / 决策 / 演进的去处 = 流水账**（`log.md`）+ 版本历史。

**自查 grep**，正文命中应为 0：`拍板|推翻|改回|曾定|被否|某某确认`

## 自查姿态

宣告完成前自问：

> **"如果他追问『确定一点问题都没有？』，我能拿出哪条 grep 输出 / 截图作证据？"**

拿不出 → 没查完，**不许宣告**。

把追问内置成自己的动作，**不等他问**。
