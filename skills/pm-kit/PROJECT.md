# 项目适配层（PROJECT.md）

> **这是整套 kit 里唯一需要你改的文件。** 其余所有规则、步骤、模板都不含任何项目专有信息，
> 它们要用到「这个项目的事实去哪查」「用什么组件库」「产物放哪」时，一律回来读这一份。
>
> **填法**：每一节都有「填什么」和「填不出怎么办」。**填不出就照那条写"未接入"，不要编**——
> 编一个看起来合理的信源，下游会照着它去查，查不到时以为是自己的问题。
> 全篇 `{{ }}` 是待填槽位，`<!-- 范例 -->` 段是某个真实项目填好的样子，照着改。

## 一、产物落点

| 项 | 值 |
|---|---|
| 需求根目录 | `{{ requirements/ }}` |
| 单个需求的目录结构 | `{{ 见下 }}` |
| 交付类产物落哪 | `{{ deliverables/ }}` |
| 过程类产物落哪 | `{{ process/ }}` |
| 一次性、不进版本库的 | `{{ .tmp/（需已 gitignore）}}` |

单需求目录约定（kit 默认，可改）：

```
{需求根}/{分层…}/{需求目录}/
├── _index.md          ← 元数据 + 状态真值 + 已定事项 + 过程产物索引
├── log.md             ← 操作流水（追加型，最新在前）
├── deliverables/      ← 下游拿去干活的：requirement.md · page-specs/ · 原型 · 模板件
├── process/           ← 产上面那些东西的中间账本：steps/ · refs/ · assets/
└── .tmp/              ← 约束账本、实测凭证等一次性件
```

**判据一句**：这份东西，下游要拿去干活吗？是 → `deliverables/`；不是 → `process/`；**判不出 → `process/`**
（放错 process 只是下游少看一份，放错 deliverables 是把没按交付标准写过的东西发给研发和客户）。

**目录分层**（按版本 / 按月 / 按人 / 不分层）：`{{ 填你们的 }}`

## 二、事实信源分级（最重要的一节）

需求设计里 90% 的错来自「**现状是什么**」判错。这一节告诉 kit：这个项目里，各类事实各自去哪取、
哪个信源能承担哪一级断言。**`evidence.md` 全靠这张表运转。**

| 要判的事 | 去哪查 | 这个信源能证明 | **不能**证明 |
|---|---|---|---|
| 有没有这张表 / 这个字段 / 这个接口能收什么 | `{{ 后端契约在哪：本体快照 / OpenAPI / DB 文档 / 代码仓 }}` | 后端契约 | 前端有没有把它放出来 |
| 这一页现在长什么样、某个入口在不在 | `{{ 前端现状去哪看：真实页抓取 / 前端源码 / 页面快照库 }}` | 前端现状 | 后端支不支持 |
| 某个配置 / 开关 / 权限在生产上是什么值 | `{{ 生产配置怎么只读查；查不到就写"未接入" }}` | 生产现值 | 测试环境的值 |
| 设计规范（间距 / 档位 / 控件形态 / 文案样式） | `{{ 设计体系文档 / 组件库 docs / Figma }}` | 该怎么做 | 现在是不是这么做的 |
| 某段业务历史为什么这么定 | `{{ 需求库 log / 决策记录 / 会议纪要 }}` | 决策过程 | 当前现状 |

**两条通用铁律（不随项目变，写在这里是因为它们要配合上表用）：**

1. **结构看后端、现状功能看前端，各有其源不可互推。**
   后端能收 ≠ 前端已放。数据层有「隐藏/排序」字段 ≠ 界面上有那个按钮。
   这类「后端早支持、前端锁着没放开」的需求，工作量主体全在前端，
   **绝不能因为后端字段存在就判「现状已有、几乎不用做」**。
2. **样本 / 截图 / 一条线上数据是「实例快照」，不是「结构定义」。**
   它能说明"长什么样"，不能说明"哪些字段固定、哪些可配置/可隐藏/动态生成"。
   要列字段清单前先读承载对象的定义，确认有没有模板化 / 自定义 / 启停机制。

**信源缺位时的三个合法出口**（任选其一，**不许硬写**）：
① 标「现状基线待实查」；② 写进研发开工自查项并注明"若与此不符属范围变化、须回报"；③ 直接问人。

<!-- 范例
| 后端契约 | 后端源码仓 / 接口文档（对象定义 · 接口契约 · 业务规则）|
| 前端现状 | 前端源码仓；或对着运行环境抓真实页、存成页面结构文档 |
| 生产配置 | 配置中心只读 API（凭证每次现场问、绝不落盘）|
| 设计规范 | 组件库文档 / 设计规范站（组件 API · Design Token）|

## 三、设计体系与原型渲染栈

`pm-prototype` 的方法论（信源纪律、验证力、概览页、红点标注、场景分页）与本节无关；
本节只管「**用什么画**」。填不了就选「纯 HTML/CSS 兜底」，方法论照样成立。

| 项 | 值 |
|---|---|
| 组件库 | `{{ 库名 + 版本 + 文档在哪；无则填「无，用语义化 HTML + 一套极简 CSS」}}` |
| 引入方式 | `{{ CDN 地址 / 本地 lib/ 目录；离线要求？}}` |
| 允许外链域名白名单 | `{{ 列出；原型必须能离线 file:// 打开的话，依赖要本地化 }}` |
| 页面类型字典 | `{{ 有没有「列表页 / 表单页 / 详情页 / 报表页」这类版式规范？在哪查；无则填「无」}}` |
| 端形态 | `{{ 只有 PC？PC+H5？各自视口 }}` |
| 演示壳（场景切换侧栏） | `{{ 有模板就指路；无则按 pm-prototype/references/demo-shell.md 现搭 }}` |

**填「无」不影响主流程**：没有组件库时，原型用语义化 HTML + 一套克制的 CSS 也能承担它的职责
（给人看、能验证价值、能逐页确认）。**不要因为没有组件库就跳过原型。**

## 五、状态流与闸门档案

kit 默认状态流（改动前想清楚，下游都按它判）：

```
draft → ready → prototyped → done
```

| 状态 | 含义 |
|---|---|
| `draft` | 已登记，需求正文未定稿（含原型迭代全程）|
| `ready` | requirement 五段完整 + 阻塞型闸门全过 |
| `prototyped` | 原型已产且实测通过 |
| `done` | 验收签核完成、交付关闭 |

**闸门档案**（几道闸、哪些阻塞，改这里即可，`review-gates.md` 读它）：

| 闸 | 名称 | 何时 | 阻塞？ |
|---|---|---|---|
| G1 | 探索确认闸 | 七要素收齐、真问题定位后 | `{{ 是 }}` |
| G2 | 影响面确认闸 | 类型判定 + 波及面盘完后 | `{{ 是 }}` |
| G3 | 方案核对闸 | 页面/能力改动清单逐条确认后 | `{{ 是 }}` |
| G4 | 收口评审闸 | 五段成文组装完、推 ready 前 | `{{ 是 }}` |

`review_phase` = 已过的**阻塞型**闸门数；`status=ready` 要求 `review_phase == 阻塞闸总数`。
