# 原型的两条命脉：信源真 · 验证得了

---

## 一、信源纪律：每个元素都要能溯源

原型是给业务看的高保真演示——**高保真的前提是不臆造**。

每个页面 / 字段 / 交互 / 文案都要能答"这是从哪来的"，答案只允许两种：
**该端真实页某处**，或**需求某条**。答不出 = 凭印象编的，删掉或去补信源。

### 三种最顺手的臆造，逐一堵死

1. **规格里"如 / 例如 / 示例"引出的是演示素材，不是默认配置。**
   字段说明写"显示名如'甲''乙'"是举例，别把"甲""乙"当默认字段填进页面。
   **默认值 / 默认字段必须有规格里"默认"字样的条文撑腰，查不到就不是默认。**

2. **逐页取该端真实页，禁用一页推断其余。**
   别抓了填写页就把详情页脑补成"填写页的只读版"——
   **页面形态差异往往恰在最不像的那页**（详情 / 报告页常是多栏报告，跟表单结构完全两回事）。
   每端也各用**该端**真实页做基准：移动端不是桌面端缩窄。

3. **动手前从规格把该元素的约束拉成清单逐条核。**
   **自己刚写过的规格最危险**——记忆里最先丢的就是"只读块不重复显示分数""某标签不加"这类约束细节，
   凭记忆重画必违约。

### 撞见真实页与需求打架 → 回写需求

**真实页是需求的免费校验器。** 改需求并记一笔变更历史，别在原型里把它抹平。

### 快照是采集制品，不是真相 oracle

嵌入真实页快照时，允许修正的只有**采集失真**（图标字体被裁、表头中间态、列宽被抓窄）；
**不允许改变真实页的功能构成**。

**判断原型对不对，基准是真实页面，不是手上这份快照。**

## 二、demo 的验证力：先判它要验证什么

默认惯性是把页面长相画出来、每页塞一份写死的示例——
这演示了"长什么样"，却**对核心价值是盲的**：文字对布局盲、死数据对"配置生效"盲。

动手前先判这个 demo 要验证什么，再让它真验证得了。

### 类型一 · 体验密度型

**什么时候**：报表 / 多维筛选 / 多层树 / 长表单——**扫视效率、页面长度、层级可辨本身就是要验证的价值**。

- 用**真实数据密度**渲染，不是 3 条示例，是客户真实量级（几十个指标、多层树）。
- 以目标用户身份把页面"用一遍"：要滚多久？找得到要操作的东西吗？层级挤压会不会看错对象？
  **文字层"逻辑自洽" ≠ 画面层"用得下去"。**
- 有竞争方案就都画出来并排比，**别凭文字拍板**。画面暴露的方案问题回写需求 / 当场换向。
- **带分页的选择容器也属这一型**：模拟数据必须 **> 每页条数**——
  分页 / 清空 / 已选计数这些形态**有量才出现**，几条示例既画不出分页，评审也审不出缺分页，
  缺陷会一路留到测试期。
- 模拟数据用**生成式**（循环生成，前几行手写真实语义、其余生成），**禁逐行手写字面量数组**。

### 类型二 · 可配置 / 联动型

**什么时候**：模板 / 表单 / 门户 / 权限显隐——**"改配置后渲染跟着变"才是核心价值**。

死数据页对这价值**零验证**。demo 必须打通「配置端 → 渲染端」真联动，**先定配置模型再画页面**：

1. **配置模型单一来源**——渲染端的配置数据结构与配置端同构，别两边各写各的；
2. **同源桥**——配置端把配置写进本地存储，渲染端读取渲染；渲染端带默认兜底 + 手动"重新读取"按钮；
3. **渲染写成条件函数**（按配置项驱动）而非硬编码分支——任意配置组合都能现场"改配置看效果"，
   评审可自助验证；
4. **配置端与渲染端各自独立文件**，天然隔离。

> 桥是**演示机制，不写进需求**；规格层表述为"按发起快照渲染"等产品语义。

### 类型三 · 任务克制型（所有页面 / 弹窗，默认必做）

**"看上去内容很多，但是不好用"是照单全画的高频反噬。**
把需求里的信息照单全画进一屏，是在演示"信息完备"，不是在演示"用户用得下去"。

以目标用户身份走当前任务，问 **"这一屏我要决策 / 完成什么？"**：

- 第一层只保留完成该步**必需**的信息与操作，其余收进二级（展开 / 更多 / 提示 / 详情跳转）；
- **弹窗只服务一个决策**。同屏堆出多组长清单（"会影响的 + 不影响的 + 流程说明"三段并列）
  → **这是设计问题不是绘制任务，先质疑再画**；
- 信息过载属"画面暴露的方案问题"：**回写需求做信息分层，不照单全画**。

### 类型四 · 文案语域与精炼（所有界面文案，默认必做）

上一型管信息结构，本型管**文案本身**。弹窗即使只服务一个决策，
把需求影响面逐条转抄成正文照样是糟糕体验。

**两条判据**：

1. **读者是最终用户，不是规格读者**——出现"接口 / 字段 / 页签下勾选清除"类实现语汇，
   或单条文案折行 ≥2 行 = **语域错了，回改**；
2. **形态与长度对齐该端真实页同类场景**——删除确认 = 短形态
   （标题 + 一两句"删除后无法恢复" + 确认/取消）；
   警告条 + 影响清单 + 勾选框这类重型模式**须有真实页信源撑腰**，答不出 = 按信源纪律删掉。

**规格推导的边界行为各有去处，不进界面文案**：
评审要看的进「本页改造说明」面板，开发要看的留规格与核销表。

## 三、保真度底线

### 可操作元素真能操作

把原型当真页面，**每个像按钮 / 可操作的地方都点一遍**：
新增 / 删除、排序、可重复块（上限）、折叠展开、切 tab——**是否真响应、真增删、真体现上限**。

点了没反应的死文字占位（如固定"＋新增（1/5）"）就是空壳，**补成数据驱动**。

逐条对照需求里的交互词（"可重复""最多 N""可排序/增删"）确认原型真实现，**而非文字提了一下**。

### 操作密度

同页 ≤3 主操作；表格操作列可见按钮 ≤3，超出收「更多」。
**任何位置无一行平铺 4+ 按钮。**

### 视觉异常先证伪自己，别先甩锅环境

有人报"某处冒出小方块 / 错位 / 叠字"时，**第一反应是查自己的布局**，
不是断定"浏览器插件注入、我复现不出"然后加段抑制样式糊弄过去。

**关键陷阱**：**异常那一点查不到节点 ≠ 不是我的问题**——
溢出、裁切、负边距、定位错位都制造"视觉上有、那一点没有元素"的假象。
必须补查**相邻元素的实际渲染宽度 / 位置**。

一行挤不下的三件套：① 容器有没有换行 ② 子项宽度合计是否超容器 ③ 盒模型算法。

> "环境问题"是高风险万能借口（不可证伪、能甩锅、还能解释"复现不出"）——
> **只在穷尽自身代码后才用，且必须诚实标注"疑似、未复现"**。
