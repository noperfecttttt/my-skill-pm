# 方案设计：从哪起跳 · 做到哪一档 · 19 条设计原则

> **何时读**：方案核对那一步动笔前；任何时候要说"建议这么做 / 需要新增 X"之前。

---

## 一、第一锚点是既有系统现状

**起跳点必须是「目标系统现在怎么承载这件事」**（既有功能 / 数据结构 / 工具形态 / 既定约定），
让既有实现成为设计的第一性约束。

业界做法 / 领域通识 / 理想方案只作**参照系**对照差异，**不作骨架起点**。

- 表面语义差（"等级" vs "类型"、"通用做法" vs "我们的工具"）常非真冲突，底层结构多已能容纳——
  **先扫既有，再下"需新建 / 有冲突"的结论。**
- **越是"我很懂这个领域"的需求越容易从通识起跳、跳过既有**，越要先产出
  「既有在这件事上已有什么」的实查清单。**没这份清单不准提方案。**

---

## 二、要最优解，不要最小改动

> 来源：一次真实反馈——「过于保守，是最小改动量而非整体框架下的最优解」。

**方案段必须先给最优解，再给成本裁剪档。**

- ❌ 禁用"复用已有能力 / 改动最小"替代最优解。
- **平台已有能力是约束，不是方案上限。**
- 否定对方提的方案时，只能否定它**单独成立时**的效力，不能因此不给更好的。
- **出现"逐列指定 / 特例 / 兜底"即抽象层次不够**，回去重抽象。
- **范围扩张 ≥2 次 → 回头重审抽象层**（多半是切面切错了）。

形态：先写"最优解长什么样"，再写"如果只给 X 成本，砍掉哪些、保留哪些、代价是什么"。

---

## 三、然后取最小增量阶梯（与第二条不矛盾）

第二条管**"往哪个方向做"**，本条管**"这次做到哪一档"**——先想清最优解，再选落地档位。

适用于**增量 / 增强 / 补一环**类需求（在已有功能上加东西，而非全新模块）。

**优先级阶梯（默认从最小档试，够用即停）**：

```
在现状产物/字段上扩展  >  现状流程里加一步  >  加配置项  >  新增入口/动作  >  新增页面/模块
```

做法：先写一句「**现状是怎么跑这件事的**」（哪条链路 / 哪个动作 / 产出什么），
再问「缺的这一小块加在这条链路的哪个最小点上」。

- **现状已具备的能力**（异步 / 性能 / 权限 / 通知 / 下载 / 分页），实查确认后
  **降为"复用现状 X"约束，不单立新故事**。
  一个故事成立的前提是带来现状没有的能力；描述的若是现状本就在做的事，
  **删故事，改写成复用约束**。
- **「加控制 / 限制 / 管控」类需求，粒度也分最小档**：先问控的是「**谁能用**」还是「**用多少**」——
  成本顾虑容易让人直接上"额度 / 配额 / 计数 / 超限"整套计量系统，
  但真实诉求常只是"收口到特定人"。默认从**控人**起步（挂一个开关 / 权限点，
  复用已有权限引擎，不重建框架），够用即停；确有计量诉求再升档。

---

## 四、承载形态是体验意图，不是技术选型

承载形态（弹层 / 抽屉 / 新标签页 / 同页跳转 / 链出既有页）承载的是**用户的体验意图**。

- 对方说过"新开页面 / 弹窗 / 就地"就**按他的原话**。
  "有现成组件 / 回填零成本 / 平台一致"只是实现便利，**便利不能凌驾已明确表达的意图**。
- **创建 / 编辑类目标页若平台已有成熟页，默认「新标签页 / 链出既有页 + 回来刷新带入」，
  不内嵌重画表单**——"组件现成"常诱导把本不属本需求的既有页表单拉进来重设计，越范围又返工。
- 承载二选一请人拍板时，**把他先前的原话意图写进选项标签**
  （如"选项 B·你说的新开页面"），意图与代价并列摆出，别只用技术措辞诱导。
  一次讲清多半一次定案，省掉整套按错误承载落地后的返工。

## 五、19 条产品设计原则

> **编号仅用于内部覆盖度自检，禁止出现在交付产物里**——读者从编号读不出任何内容。

### 思维篇（落探索期的追问与判定）

| | 原则 | 要点 |
|---|---|---|
| T1 | 一切皆产品 | 要独立、不暴露内部、可靠、清晰适用 |
| T2 | 业务场景是产品的基础 | 逐层 why 追真问题（不固定层数）；先故事再详设 |
| T3 | 彻底解决问题 | 先思考彻底，再考虑临时；临时方案不允许孤立存在 |
| T4 | 差异化是本质 | 业务深度理解 + 工程能力 + 长期实践 |

### 功能篇（落边界与功能说明）

| | 原则 | 要点 |
|---|---|---|
| F1 | 面向组织设计 | 客户是组织不是单用户；多角色协同 |
| F2 | 万人使用原则 | 按 1 万人设计；批量 / 自动化；并发稳定性 |
| F3 | **没有人会改默认设置** | **默认即最佳实践**；增设置项务必谨慎；场景模板 > 自定义。字段默认值**禁写"待用户配置"** |
| F4 | 安全和稳定大于一切 | 稳定 / 安全 > 创新；AI 能力是新挑战面 |
| F5 | 不要轻易下线和降低功能 | 下线**必须给替代方案**——显式不交付项要配套替代 |

### 交互篇（落页面规格）

| | 原则 | 要点 |
|---|---|---|
| I1 | **如非必要勿增新页面** | 每页要有独特意义；先回顾已有页面。完全新增必须证明无页面可承接 |
| I2 | 习惯路径 > 少点一次 | 同类同交互；**不为少点一次而在同页堆操作**（同页 ≤3 主操作）|
| I3 | 所有对象都可以打开 | 每个对象有详情页；展示统一 |
| I4 | 让用户觉得可控 | 操作前预期清楚；重要操作二次确认；有撤回路径；删除进回收站 |
| I5 | 符合直觉 > 帮助提示 | 优先既有模式；独有操作大概率"见得少" |
| I6 | 提示，**并给出解决方案** | 表单错误要能锚点定位；**不光给清单，还要给操作** |

### 内容篇（落业务概念与文案）

| | 原则 | 要点 |
|---|---|---|
| C1 | 谦逊但平等 | 用"你"不用"您"；建议性描述；少用感叹号 |
| C2 | 概念清晰一致 | 维护业务概念树；常用动作统一（创建 / 新建 / 添加 只用一个）|
| C3 | **拒绝隐性知识** | 隐含 = 意外和惊吓；**预制逻辑必须显式告知** |
| C4 | 国际化是必选项 | 必选不是补充；中文先简化再翻 |

### 收口时的覆盖度自检

| 内容块 | 应体现 |
|---|---|
| 用户故事细化 | T1 F1 T3 C3 |
| 页面功能说明 | I1 I2 I3 I4 I5 I6 F3 C1 C3 C4 |
| 全局前提与约束 | F2 F4 F5 C3 C4 |

**内化体现，不外显编号**：模板结构里的列 / 行 / 子项本身就是原则的物化
（如操作按钮表的"二次确认 / 撤回"列体现 I4）。

## 六、技术问题不进需求阶段

**判据（唯一）**：把两三个候选答案代入，**他在界面上、在业务规则上看得出差别吗？**
详见 `ask-or-not.md`。

**需求阶段不负责回答"怎么实现"，四类**：
① 用哪个技术手段达成 ② 数据怎么存 ③ 字段级取值与传参 ④ 代码或数据层的既有不一致
（除非它改变了业务口径，那按"要不要连带修"的**范围问题**问）。

**这四类不是需求文档的缺口，是研发的设计工作。**

> **完备标准是"业务上无歧义"，不是"实现上无选择"。**
> 研发看完需求仍要做技术设计，这是正常且必要的。
> **研发会问实现细节 ≠ 需求文档有缺口**；
> "怕不写清楚被研发问"不构成攒技术问题的理由。

**有业务后果的技术选型，上浮的是业务后果不是方案**：
"名字关联有重名错发风险，能接受吗？"可以问；"选名字关联还是接口对接"不可以。
