# 步 0 · 需求登记

## 做什么

1. **扫近重**（先于建档）
2. **定两个名字**
3. **建档**
4. **问清两个只能由人给的字段**

---

## 1. 扫近重（开新条目前必做）

扫一遍需求总表，判断本需求是否与已有条目同题 / 近重。触发信号：
同一主题已有条目 / 描述"听起来之前做过" / 对方说"再做一版、换个做法"。

**命中近重不自己拍板怎么处理**，把三选一摆出来并讲清各自后果
（会不会产出两份重复资产、旧资产怎么处置）：

| 选项 | 后果 |
|---|---|
| ① 在旧条目上调整 | 历史连续，但旧条目已定稿的部分要重新过审 |
| ② 另起独立新条目 | 标明与旧条目的**唯一差异点**；两份资产并存 |
| ③ 旧条目作废、本条替换 | 旧条目的下游引用要一并处理 |

> **差异点（哪怕只有一句话）往往就是这条新需求存在的真正理由，抓它当主线。**

## 2. 定两个名字（一次定齐）

每个需求有**两个名字，职责不同，别混用**：

| | 给谁用 | 会不会变 |
|---|---|---|
| **目录名** | **人**——翻目录、按业务名检索 | 可能变（标题演进时）|
| **标识（slug）** | **机器**——主键、跨需求引用、下游分发 | **永不变** |

- **目录名** = 中文需求标题，≤20 字；路径非法字符要清洗（`/` → 全角，`\ : * ? " < > |` 去掉）。
  标题超 20 字就压缩，留「主体 + 关键变化」。
- **标识** = `{type}-{name}`，type 限 `feat`（新功能）/ `opt`（优化）/ `fix`（缺陷修复），
  name 是语义化英文短横线串。**先定中文标题，再由标题拟英文标识**（语义翻译，不是音译）。

两者同时落盘，并一起复述一次：「目录叫『{中文标题}』，内部标识是 `{slug}`」。不反对即采用。

**标识一经确定永不改名。** 发现它已描述不了需求范围时，**记一条流水说明偏差即可，不改字段**——
下游都拿它当稳定 key，改它等于打断机制。

> **标题后来变了，目录名默认不跟着改**——目录名是定稿时的快照，准确性由 frontmatter 的 `title` 承担。
> 改目录名要连带替换全库路径引用，代价远高于"名字不够新"。

## 3. 建档

按 `../../pm-kit/templates/_index.md` 建 `_index.md`，同时建齐 `deliverables/`、`process/` 子目录。
落点与分层读 `../../pm-kit/PROJECT.md §一`。

**产物归属一问**：这份东西，下游要拿去干活吗？
是 → `deliverables/`；不是 → `process/`；**判不出 → `process/`**。

## 4. 问清两个只能由人给的字段

### `target_release`（目标版本）
未定就标「待定（定稿前确认）」，别猜。

### `committed`（这一版是不是对外承诺过要交付）

**为什么要单独有这个字段**：`target_release` 只说"排哪一版"，不说"这一版答应过谁"，
**两者刚性完全不同**。一批需求整批延期时，从产物里看不出哪些是承诺过的。

- **值只能由人给，AI 不推断。** 优先级高、状态靠前、排期靠前，**都不是**判据——
  承诺是对外做出的约定，产物里看不出来。
- 问不到就写 `false` 并挂一条待确认，**不许留空、不许猜 `true`**。
- `true` 时 `committed_note` 必填：向谁承诺、谁拍的、哪天。

**两个必问时点**：
1. **建档定 `target_release` 时**（定版本和定承诺是同一次对话里的事，一起问）；
2. **改 `target_release` 时**——原来 `committed: true` 的要延期，
   **先把"这个承诺怎么办"摆出来**：解除承诺，还是承诺跟着挪到新版本。流水记下他怎么答的。

> 批量延期报清单时**先按 `committed` 分组**，承诺的单独列在前，不混报总数。
