# PM 需求设计 Kit

一套**平台无关**的产品需求设计工作流，从「一句话诉求」跑到「可交付的需求文档 + 可确认的原型」。

抽取自一个真实运行了半年多的需求工作流，剥离了平台专有部分，
所有项目专有信息收敛到**一个** `PROJECT.md`。

---

## 三步移植

### 1. 复制

把 `skills/` 下的**四个目录**整个复制到目标项目的 `.claude/skills/`：

```
目标项目/.claude/skills/
├── pm-kit/           ← 共享层（没有 SKILL.md，不会被当成 skill 加载）
├── pm-requirement/   ← 主干：需求分析
├── pm-prototype/     ← 原型生成
└── pm-review/        ← 交付前验收
```

> **四个必须一起复制**——三个 skill 都按 `../pm-kit/...` 引用共享层。

### 2. 填 `pm-kit/PROJECT.md`

**这是唯一需要改的文件。** 六节，从上往下填：

| 节 | 填什么 | 不填的后果 |
|---|---|---|
| 一 · 产物落点 | 需求放哪、目录怎么分 | 产物会落得到处都是 |
| **二 · 事实信源分级** | **最重要**：平台现状去哪查、哪个信源能承担哪一级断言 | 「现状是什么」会靠猜——这是需求设计里 90% 的错的来源 |
| 三 · 设计体系 | 用什么组件库、怎么渲染原型 | 填「无」也能跑，原型用语义化 HTML |
| 四 · 角色 | 谁拍板、有没有外部客户 | 决策分流会少一档 |
| 五 · 状态流与闸门 | 几道闸、哪些阻塞 | 用默认的四道即可 |
| 六 · 本项目"别踩" | 踩过的坑，随用随加 | 同一个坑会被踩第二次 |

**填不出就照那条写"未接入"，不要编**——编一个看起来合理的信源，
下游会照着它去查，查不到时以为是自己的问题。

### 3. 试跑一个小需求

拿一个真实的小需求跑一遍 `/pm-requirement`，把 `PROJECT.md` 里填不准的地方补上。
**第一个需求跑完，适配层基本就稳了。**

## 三个 skill 怎么配合

```
/pm-requirement   登记 → 探索 → 影响面 → 方案核对 ─┬─→ 收口成文
                                                    │
/pm-prototype                        原型迭代 ←─────┘（主线，不是可选项）
                                                    │
/pm-review                              交付前四视角验收 ←┘
```

产出：`requirement.md`（五段）+ `page-specs/*.md`（逐页规格）+ 原型 + 流水账。

---

## 它凭什么比"让 AI 写个需求文档"强

不是模板更全，是**把踩过的坑做成了动笔前的判据**。几条最值钱的：

| 规则 | 治什么 |
|---|---|
| **该不该问**（`ask-or-not.md`）| 技术题一旦摆进决策列表，对方答不了、只说"我不懂"——**那个决策就 100% 由 AI 代决了**，而且是在所有人都以为"已经确认过"的情况下 |
| **先自答三格** | 被迫先写下"我的答案"，问句就自然产生不出来了。**规则要靠记得想起来，格子是写的动作本身** |
| **宁缺勿编** | "看起来合理的默认值"最像真的、最易被信任。**留空会被追问，假值会被当结论传到开发照着建库** |
| **作用域纪律** | 断言的作用域不得超过信源。**减法比加法危险——加错了下游会发现，删错了下游只会觉得"本来就没有"** |
| **查证前先问收益** | 说不出"这次查证会改变需求里哪一句话"就别查。**后面四问都是许可式，动手那一刻总编得出理由** |
| **条目准入** | 不先立尺子就批量产条目，必然碎、重叠、失衡，而**自由发挥的产物长得跟合规产物一模一样** |
| **规则来源四问** | 把对界面的每一句纠正都记成业务规则 = **把"我犯的错"变成"业务约束"**，研发会当本期新需求去实现 |
| **原型先行 + 回写** | **他是对着原型点头的。** 从第 2 轮起他的每次调整都是指着页面提的——改的是原型，规格必须跟着改 |
| **渲染层视角** | 三视角全过 + 断言全绿 + 零报错，业务方打开浏览器一眼就看出问题。**文字层的检查对渲染层结构性失明** |
| **停点汇报骨架** | "说人话"这类叮嘱在长指令下必失守。**固定模板把合规从"记得住"变成"照着填"** |

## 目录

```
skills/
├── pm-kit/
│   ├── PROJECT.md              ⭐ 唯一要改的
│   ├── rules/
│   │   ├── ask-or-not.md       该不该问（决策分流）
│   │   ├── evidence.md         宁缺勿编 · 信源分级 · 查证准入 · 作用域
│   │   ├── expression.md       说什么话 · 什么形态 · 要不要有这段
│   │   ├── item-admission.md   条目准入（故事 / 规则 / 页面说明的尺子）
│   │   ├── solution-design.md  最优解 · 最小增量阶梯 · 19 条设计原则
│   │   ├── review-gates.md     闸门怎么过 · 占位健康度 · 快车道
│   │   ├── stop-report.md      停点汇报骨架 · 弹题判据
│   │   └── final-audit.md      终审电池 · 影响面盲区 · 只写现状
│   └── templates/
│       ├── requirement.md      五段结构
│       ├── page-spec.md        逐页规格
│       ├── _index.md           需求元数据
│       ├── log.md              流水账格式
│       └── solution-overview.md 方案概述四节
├── pm-requirement/  SKILL.md + steps/0~5
├── pm-prototype/    SKILL.md + references/（原则 / 概述页 / 演示壳 / 自检）
└── pm-review/       SKILL.md
```

## 没有移植的部分（有意为之）

| 没带 | 为什么 |
|---|---|
| 本体 / 领域快照查证机制 | 高度平台专有。**方法论保留在 `evidence.md`，机制交给 `PROJECT.md §二`** |
| 具体组件库、页面类型字典、原型渲染栈 | 同上，交给 `PROJECT.md §三` |
| 二开 / 报价 / 对照卡那条线 | 商业模式专有，与"需求设计"正交 |
| 各类校验 hook、计时器、提交脚本 | 依赖具体运行环境；**清单化的自检比 hook 更可移植** |
| 环境噪音排障记录 | 只对原环境成立。`PROJECT.md §六` 是留给你自己攒的 |
