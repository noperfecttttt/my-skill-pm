# 条目准入：批量产条目之前先立尺子

> **何时读**：凡是要"一条一条批量产"东西的地方——写用户故事、立业务规则、写页面功能说明、
> 列验收场景、列异常场景。**动笔前先写下三答，产完再拿它回筛。**
>
> **为什么必须先立尺子**：不先定组织方式就动笔，只会边写边随意发挥——切法混用、
> 把复述升格成规则、单章塞爆。产出必然碎、重叠、失衡，而返工时挪位置、改编号、调排版都治不到根。

## 三答（动笔前写下来）

- **准入**：什么才算一条？不够格的不写。
- **维度**：按什么切？只用**一个**维度，别页面 / 动作 / 子类型混着切。
- **落点**：一条放哪？只放**一处**。

> **数量 / 体积异常 = 失控信号**：用户故事超过 ~10 条、业务规则上几十条、单章挤进多页细节、
> **分册数明显多于真实页面数** → 回三答重筛（大概率混了维度或收进了复述），
> 别先去挪位置改编号——那是根之下的枝节。

---

## 三类高频产物的尺子

### 1. 用户故事（US）

| | |
|---|---|
| **准入** | 一条能独立走完的**用户主流程** |
| **维度** | 一个完整用户目标一条线。向导的某一步 / 某个子类型 / 单个控件**都不是** US |
| **落点** | 完整叙事落主承载页面的规格；编号作贯穿锚点 |

**自检**：念一遍"作为…我要…以便…"——两条的"以便"相同 → 合并；
US 名里出现「Step X / 某某类型 / 某控件」→ 它不是 US，细节下沉到页面功能说明。

### 2. 业务规则（BR）

**先答来源，再谈判据。** 这条约束**从哪来**？来源是事实题，比"有没有业务后果"这种判断题好答，
也拦得住下面三判据拦不住的那类：

| 来源 | 处置 |
|---|---|
| ① **平台已经这么做了** | 写进现状 / 交互说明，**不占规则编号** |
| ② **设计规范这么要求**（档位、文案样式、控件形态）| 遵守它。**规范不需要在每个需求里重申一遍** |
| ③ **他纠正了我的产出** | 先分辨纠正的是什么：纠正"你没按规范做" = 我的错，改产出、**不立规则**；纠正"业务上该是什么" = 才立 |
| ④ **本期新定的业务决策** | 立规则 |

> ③ 最容易失守：**把对界面的每一句纠正都记成业务规则，等于把"我犯的错"变成"业务约束"，
> 研发会当成本期新需求去实现。**

来源过关后再过三判据，缺一不写：

1. **有业务后果**——驱动校验 / 状态流转 / 权限 / 字段联动 / 边界异常之一，说得出"它改变了哪个开发或测试动作"；
2. **非复述**——字段表 / 交互说明能直接推出的不另立（"必填缺失阻止下一步"字段表已有）；
3. **删了会有人做错**——删了没人错的是噪音。

**落点按作用域定**：只影响一页 → 那页规格的「业务逻辑」节；≥2 页或跨业务 → 全局规则；
公共需求节只留**按类聚合的索引**（类别｜编号｜定义在哪），**不放定义**。
理由：多数规则只影响一页，全放公共节会让人一口气读十几条与当前页无关的规则。

> **收口复查问的是"这条从哪来"，不是"这条写得清不清楚"**——把一条不该存在的规则写干净，它还是不该存在。

### 3. 页面功能说明

| | |
|---|---|
| **准入** | 每页四件齐：**元素 / 文案 / 交互 / 业务逻辑**（最后一件最易漏）|
| **维度** | 按页切，每个独立交互单元（含抽屉 / 弹窗）一份 |
| **落点** | 恒组装成单页单文件的分册（1 页也分册），跨页共性归公共需求节 |

整页复用既有能力的页只写"复用谁 + 上一步给什么 / 下一步产出什么 + 本页特有"，通用交互不重复搬。

### 第四答 · 分册准入：这条内容，用户在哪个界面感知到？

- 只在**一个**界面 → 归**那页分册的小节**（含抽屉 / Tab / 落库 / 异步进度 / 完成通知）
- 在 **≥2 个**界面 → **公共需求节**，各页引用不复述
- **完全没有界面** → 才独立成册，且只有闭集几类（对外接口 / 导入导出 / 定时任务 / 平台配置）

> **为什么要卡死**：把计费、落库、完成通知、异步任务、审核抽屉各拆一份，分册数量会翻倍失控。
> 每条拆分规则单看都对，合起来就失控——而**没有一条规则回头问"这个需求一共几份、读的人受得了吗"**。

## 业务规则的形态：分类先行

写规则之前先答一句「**这个需求要在哪几方面立规则**」，得到 3~8 个类别，再逐类往下写。

- **第一类固定是「核心口径」**（这个需求最本质在改什么，通常 1~3 条），边界 / 叠加 / 异常另立类。
- 类别**从本需求内容里长出来**（入口与权限 / 内容去向 / 失败处理），不是套通用框。
- **防退化三条**：一类 ≥2 条（只有 1 条的并进最近的类）｜类别 ≤8（超了回头合并）｜类名用业务话。

> **分类本身是体检**：同类堆一起，归属问题自己就显形了——
> 若整类都在说"本需求不改 X"，一眼看出该移去「本期不做」。

**编号纪律**：纯连续、同类连号、类间接续。定稿前可自由重排；
**定稿后补规则 → 追加到末尾**，索引写成 `BR-04~09、BR-25`，**不重排、不动任何既有引用**。
删条目要重排编号——**编号断档是"删过条目但没回头收拾"的信号**，而下游按编号做覆盖对账，
断档会让人以为漏了条。

## 定义行与引用行形态分开（必守）

- **定义**：`- **BR-XX｜` 起头。一条规则在整个交付包里**只有一行长这样**。
- **引用**：一律写在句中（`（BR-12）`、`见 BR-12`、表格单元格里），
  不得用行首 bullet + 编号起头；**也别把编号挂在条目末尾**当定义
  （`- **上线初始状态**：…（BR-21）` 读起来像引用）。

> **为什么要分**：分开之后"这个编号在哪定义的"是一次纯字符串比对，机器接得走——
> 引用了却没定义、删条目留下断链这类问题就不必再靠人逐份读。
> 混着写则两者不可分辨，这个活只能留给眼睛，而**看的人每轮换一双**。
> 形态统一是让机器能接手的前提，不是格式洁癖。

## 约束账本：写约束时同步记一行

**治什么**：同一交付包里两处规定互斥、而各自都自洽——这是收敛拖不下来的典型形态。

典型：规则「禁读某份缓存」⟂ 能力前提「无需额外实现」（那个能力恰好长在被禁的缓存上）；
概览「前端零调整」⟂ 页面规格要求加载态换表现。

**成因是结构性的**：规则、能力前提、阈值、概览断言**分散在不同章节**，
写规则时看不到那条前提，只有三方同时通读全文才撞见。

**做法**：凡写下**约束型规定**（业务规则 / 能力前提 / 性能阈值 / 概览的全局断言 / 明确不做），
同时往 `{需求根}/.tmp/constraint-ledger.md` 加一行：

| 编号 | 一句话内容 | 它约束住了什么 | 与已有哪条可能打架 |
|---|---|---|---|
| BR-06 | 禁读部门人数缓存 | 所有取人数的路径 | ⚠️ 能力前提「含下级无需额外实现」——含下级能力就长在这份缓存上 |

> **它是"写的时候的工作台"，不是"写完的检查清单"**：新加一行时已有约束都在同一屏，
> 填最后一列时必然扫一遍——分散在各章节时这一眼根本不会发生。
> 账本落 `.tmp/`（不进版本库、不给人读、收口即删）。

**阈值这一格可机器判，别留给人**：约束里出现「超限 / 超时 / 超过 / 达到 / 低于」这类判定词，
**同一条内必须给出数值或明确的取值来源**，否则测试造不出这个场景。

**边界要诚实**：语义互斥机器判不了，账本只是把它**放进同一视野**，仍依赖填表时真的去看。

## 拿不准的，先自答再决定问不问

写规格过程中冒出的"这里该是 A 还是 B"，默认先自己给答案（依据四选一见 `ask-or-not.md`）。
真空白也要能说出"另一种合理答案是什么、谁会选它"，说不出 = 没有分歧 = 不进待确认表。

**别把"我还没想"当成"待确认"。**
