# 交付前多视角验收

## 什么时候跑

- 原型定型、需求收口成文之后，**推进到交付状态之前**；
- 需求有实质修订之后（改过规格 / 原型的，签核要重刷）。

## 核心原则：独立性 = **信源**独立，不是读者独立

**多个视角读同一份规格，只算一道。**

四道视角里，前三道读的是**文档与原型**，第四道读的是**真实页面**——
**正因为信源不同，第四道才能发现前三道结构性看不见的东西。**

---

## 四道视角

### 视角一 · 开发（能不能照这份文档开工）

看：逻辑闭环 · 无歧义 · 下游可消费 · 完整性

**通过标准**：靠文档 + 原型**直接开发，不反复确认逻辑**；开工不被"等研发自己确认"的条目卡住。

> ⛔ **射程线（必守）**：只判「**照这份文档能不能开工**」——
> **不核实现细节、不审技术附录的证据强度**（技术附录是审计层，不是施工依据）。
> 技术事实存疑 → 归「研发开工自查项」，**不构成需求缺陷**。
>
> **为什么要钉这条**：这道视角一旦按"施工视角"核技术事实、盯着技术附录提问题，
> 主线就会为了闭环去补技术取证，下一轮它再基于新增内容提更深的技术问题——
> **技术密度螺旋走高，需求越审越像技术方案。**

### 视角二 · 测试（能不能直接写用例）

看：前后一致 · 逻辑闭环 · 边界值 · 异常覆盖 · 用户体验 · 需求↔原型一致

**通过标准**：**无歧义、无卡点、功能符合用户第一直觉**；能顺着业务主线串出端到端用例。

重点查：
- 每个能配 / 能开关 / 能删的点，**正向能力 + 反向后果 + 边界态**写全了吗；
- 空值表现 / 枚举全取值 / 分母为 0 / 失败反馈 / 动态集合退化（空集、只剩一个、输入无效）；
- 阈值型断言有数值或明确取值来源吗——**没有，测试就造不出这个场景**。

### 视角三 · 阅读者（读不读得懂）

看：一屏概览抓不抓得住 · 能不能精准跳章 · 重点突不突出 · 读不读得顺

**通过标准**：通篇是终态**无流水账**；主线故事一读就懂；形态与内容形状匹配。

**表达形态四查**（扫读面逐段过）：
1. 有没有超 3 行的单段落——有则看是不是藏着并列对象或步骤序列没转表；
2. 有没有一行箭头串表达 ≥3 步流程；
3. 有没有并列对象 × 相同属性被写成散文（读的时候要自己在脑子里建表）；
4. **反向**：有没有为一句话结论建的三行小表。

**必要性两查**：
1. **条级 · 清单型节**——「本期不做」/ 显式不交付 / 已知风险 / 全局前提，
   逐条问"读者会不会误以为它在范围内"。正文已明确的、读者压根不往那想的、
   通用免责（移动端 / 性能 / 兼容性）**一律删**；
2. **节级 · 反向查空转**——有没有哪一节在**用一段话论证本期没改它**
   （"本期不涉及 X""沿用现状、一字不动"）？那是按需节没被筛掉，**整节删**。

### 视角四 · 渲染层（照真实页核，**不得由原型作者本人跑**）

> **为什么必须有这一道**：前三道读的都是文档与规格，
> 实战里出现过**三视角全过 + 断言 44/44 全绿 + 控制台零报错**，
> 而业务方打开浏览器**两次一看即发现**问题（交互失真 / 快照丢了方向属性导致版式整片塌陷）。
> **文字层的检查对渲染层结构性失明。**

五查：

| 查什么 | 判据 |
|---|---|
| **版式双边比对** | 打开真实页与原型并排，**对关键容器取实际像素值**（宽度、字号、字重、间距）逐项比——**给数字**，不给"结构差不多" |
| **快照还原度** | 嵌入的真实页快照有没有静默丢东西（样式表拿不到就跳过、不报错）。判据：拿该模块的业务类名在快照里数"规则形"出现次数，属性里有 N 次、规则形 0 次 = 被丢了 |
| **视口可视性** | 关键内容在**视口里真看得到、真够得着**——不是"它在页面坐标系里存在"。宽表要**真能滚**（滚动宽度 > 可视宽度，且赋值后真的滚动了），不是"样式写了 auto" |
| **对偶操作逐状态试** | 有发布就试撤回、有启用就试停用、有增就试删——每个状态都点到 |
| **多承载位穷尽** | 同名动作在工具栏 / 行内 / 「更多」下拉 / 批量态各自都核过（见 `../pm-kit/rules/evidence.md §七`）|

**断言清单禁止只从规格派生**，必须含**非规格派生的三类**：
① 还原度基线 ② 对偶操作 ③ 视口可视性。且**两向验证**（正向能过、篡改能被抓到）。

> **把症状归因为"素材固有 / 环境固有"之前，先证伪自己。**

## 分级与裁决

### 视角给的是**线索，不是结论**

每条发现由主线裁决，**三个合法出口**：

| 出口 | 什么时候 | 要求 |
|---|---|---|
| **改** | 真缺口 | 落到文档 / 原型；按严重度分流——`阻塞` 必须改完才能交付，`次要` 随批修、修不完不阻塞 |
| **不改** | 越界（技术层 / 提测准备 / 必要性不过关），或文档其实已覆盖 | **必须指名依据**——哪条规则。**指不出依据 = 这条就是要改**（这一条防"不改"变成挡箭牌）|
| **删** | 指出的那段内容**本身就该删** | **删掉一条要求也是合法闭环**——不留这个出口，逐轮审下来条目只增不减 |

### 轮次分水岭

| 情况 | 下一轮 |
|---|---|
| 上轮**阻塞项为 0**（只剩次要或零发现）| **不再起轮**。次要项逐条人工确认（改 / 不改），改完重刷签核收口。**只有阻塞项能推动下一轮** |
| 轮数 ≥3 且仍有阻塞项 | **不再起轮**，交人工拍板。**建议拍板后提交，不要再跑** |

## 签核账本要自己对账

**验收材料里不含签核账本本身**——所以覆盖账本漏登记，四道视角**一条都报不出来**。

刷新签核时自己跑一遍对账（详见 `../pm-kit/rules/final-audit.md`）：

1. 规则编号 / 验收编号全集 → 逐个在账本里找得到；
2. 每张规格「字段清单」第一列 → **逐字**在字段账本里找得到；
3. 账本里的**旧版本残留**清干净——**账本是上个版本写的，它不会自己跟**；
4. 改完先空跑一次状态推进检查再宣告。

跑完 `../pm-kit/rules/final-audit.md` 的终审五步，按 `../pm-kit/rules/stop-report.md` 汇报。

> **"如果他追问『确定一点问题都没有？』，我能拿出哪条证据？"**
> 拿不出 → 没查完，不许宣告。
