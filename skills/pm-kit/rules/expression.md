# 表达纪律：说什么话 · 用什么形态 · 要不要有这段

> **何时读**：任何要产出"给人读的文字"之前——方案概述、需求正文、页面规格、原型页面说明、对话汇报。
> **产出前读，不是产完再对照**（形态是下笔前的选择，写完再改等于重写）。
>
> 三把尺各管一段，缺一把就会出一种典型的病：
> **① 用什么词**（业务语言）→ 缺了读者看不懂；
> **② 用什么结构**（形状定形态）→ 缺了内容一个不少却"又臭又长"；
> **③ 要不要有这段**（必要性）→ 缺了产物越写越厚，重点被稀释。

---

## 第一把尺 · 业务语言：按「位置」判，不按「词的出身」判

读者是产品经理和客户，必须看得懂。判据 = 这个技术名**出现在哪**。

### A. 业务描述正文 / 表格业务列 → 禁裸插技术名

**范围**：需求正文的功能说明、验收标准、业务规则、故事陈述、对话回复、页面规格派生正文。

**禁**：表名 / 字段物理名、接口路径、方法名、代码实体名、字典码、事件 topic / 错误码、
中间件与索引、DOM 类名 / CSS 选择器。

**翻译**：
- 数据流转 → "保存什么信息 / 修改什么信息 / 留什么日志"
- 约束 → 白话（"只能填英文数字"，不是正则）
- 字段 → 业务词（"序列名称"，不是 `series_code_name`）

### B. 锚点位白名单 → 技术名合法出现

这几处是给下游做追溯/设计/成本锚点用的，读者不必读懂内部：

1. 页面规格的「设计系统」行 + 组件清单：组件名**保留 + 补业务术语括号**，如 `Table（数据表格）`
2. 业务概念表的「引用源」列 / 附录的技术引用：路径**原样展示**，对象名补业务括号
3. 导入导出契约的列定义（字段类型 / 长度）：对客规格，保留白话即可
4. **技术附录（审计层）**：技术名**原样收录不翻译**，每条注明支撑正文哪条结论。
   正文指过来用固定一句：「技术依据见文末技术附录——无需读懂，供研发实施与成本追溯」

### 技术名的四条出路（按顺序试，别卡在"编个名"和"原样写"之间二选一）

| | 情况 | 怎么办 |
|---|---|---|
| 1 | 有权威业务名 | 正文用业务名，技术名进技术附录 |
| 2 | 无业务名但说得出业务含义 | 正文写业务描述（"报名方式=按名单/自由报名"，不是 `type=0/1`），技术名进附录 |
| 3 | **连业务含义都说不清** | → 读者根本用不上 → **只进技术附录，正文一个字不提** |
| 4 | 它是分类键 / 权限码 / 配置项键（**被某个机制当 key 用**）| 保留原值 + 后缀中文括号 |

> **第 3 条最常被忘**：**读到 ≠ 必须写给读者**。查到的事实，读者用不上的那部分搬进正文，
> 只增加他的阅读量，不增加他能做的判断。

**括号里的业务术语禁自拟**——查不到就挂占位 `（业务名待补）`，别自己编。

### 流程术语同样要翻译

内部工序词长得像正常中文，比代号更隐蔽——读者会以为是自己没跟上，于是不吭声地猜：

| 内部词 | 对外说法 | | 内部词 | 对外说法 |
|---|---|---|---|---|
| 收口 | 定稿 / 成文 | | 回填 | 补充 / 填回 |
| 落盘 | 保存 | | 核销 | 逐条对账 |
| 分册 | 每页一份说明 | | 占位 | 先留空标记 |
| 闸门 G2 | 影响面确认（带闸名，别念代号）| | 留痕 | 记录依据 |

**自检一问**：这段话里有没有读者要停下来问"这是啥"的词？有就补中文。

## 第二把尺 · 形状定形态

绝大多数"又臭又长"都是**形状判对了、形态选错了**——内容里客观存在一个结构
（一个矩阵 / 一组问答 / 一个序列），表达时被压平成散文，理解成本从作者转移给了读者。

| 内容形状（怎么识别） | 该用的形态 |
|---|---|
| 多个并列对象，每个都要交代同样几件事（≥2 对象 × ≥2 属性）| **矩阵表**：对象一行，属性一列 |
| 一组固定问题的答案 | **两列问答表**：加粗问题 ｜ 一句答案 |
| 有先后顺序的步骤 ≥3 步 | **编号步骤表**：步 ｜ 做什么 ｜ 在哪页/谁做 |
| 条件 → 结果的判定 ≥2 组 | **判定表**：条件 ｜ 结果/处置 |
| A 与 B 的关系 / 状态流转 | **图**（流程图 / 前后对比块）+ 挂一个真实例子 |
| 同一主题 2-4 条彼此不共享属性的要点 | **小标题 + bullet**，每条加粗标签 + 一句人话 |
| 一个结论 / 一句话规则 | **散文一句** |

### 反向闸：禁过度结构化

只知道"该结构化就结构化"会翻到另一个坑——满屏三行小表，同样难读、还更难改：

- **建表门槛**：≥2 行 × ≥2 列才建表。单行表、只有一列有内容的表 = 该写成句子。
- **一句话讲得完的不拆**：能一句话说清的结论不许拆成"标签+值"表。
- **表格内不塞长文**：**单格只承载一个值 / 一个判定**——一格里出现两件事 = 维度切错了，回去重切。
  （判据是"几件事"，不是"几个字"。）

### 两类表达面，共守形态、不共守篇幅

| | **扫读面**（扫一眼的理解工具）| **规格面**（逐字读的完备记录）|
|---|---|---|
| 有哪些 | 方案概述、需求顶部概览、页面一屏概览、界面上的说明/空态文案 | 字段清单、规则汇总、异常处理、接口规格 |
| 守形状映射 + 反向闸 | ✅ | ✅（矩阵就该是矩阵，跟谁看无关）|
| 守单段篇幅预算 | ✅ | ❌ 不设上限，只守"一格一句、一条一判定" |

**共同底线**：按**读者的理解成本**组织表达，不按"作者知道什么、引用起来方便什么"。
规格面的文字直接搬去充当扫读面，必被打回。

## 第三把尺 · 内容必要性：这段该不该有

逐条过——前几条命中就删或下沉，末条是正面（命中则补）：

1. **删了它，读者会不会误解或做错？** 不会 → 删。
2. **这段承载的事实，文档里已有一份了吗？**（载体唯一）有 → 删这份，真相留在**那一个**载体。
   跨层"概览一句 + 规格一节讲透"算新增可留；原话搬两遍不算。
   **若它其实是那个载体缺的一行/一格**（"某项不动/沿用现状"= 多一行，值格写"不动"）→ 补进去，不留散文。
3. **这段是前文规则的推论吗？**（「由此/所以」+ 结论）是 → 删。
   **但删前两步核查：有验收场景测它吗？有别处显式引用吗？任一为是 → 它是防实现错误的 why，保留。**
   （误删是正确性损失，不是省篇幅。）
4. **读者会不会压根不往这想？** 会 → 写它等于**替读者制造一个他本来没有的疑问**。
5. **这一层需要写到多细？** 同一件事在不同层出现时，每层只写该层的抽象度。
   **检验句：这一条，读者在这一层要用它做什么决定？**
6. **（正面）导读位只有编号/标题、读者看不懂业务吗？** 看不懂 → 补一句自足业务钩子；
   且**先挑支柱**（改动入口 / 核心痛点解法 / 落地前提），不列全部。

**先删后排**：必要性与形态是两把尺——**先过必要性决定留不留，留下的再排形状**。
判据一律**看形状与必要性、不看长度**：长而必要的不砍，短而多余的照删。

### 节级三态

这一节本期有内容吗？没有 → **整节不出现**（连标题一起省），不写"无"、更不写"本期不涉及 X"这类论证段。
问的是**事实题不是判断题**——"本期有没有改 X"，不是"要不要写 X"。
要提醒"某某不在范围内"的，归概览「本期不做」**一处**写清。

> **砍的是本期没动的维度，不是该写的深度**：这节没内容是因为真没改，还是因为我没想清楚？后者是缺。

### 清单型节最容易失守

「本期不做 / 显式不交付 / 已知风险 / 全局前提」——清单越长越显得完整，
于是判据被悄悄偷换成"**我们有没有做过、有没有想到**"。那是**无限集合**，按它写必然膨胀。

**正确判据永远是"读者会不会误解"。**

## 过程产物的两层结构

过程类产物（中间账本）只有两个读者：**要拍板的人**（过闸门时确认结论）与**后续步骤**（取判定值）。
所以只准有两层：

1. 「📌 给你确认的一页」——他要答的那几行；
2. 「工作底账」——下游要取的**结论行**，标明"复审可不读"。

**动作照做，过程不落盘**：自检表格、反查推导、目录原文、"查了但不涉及"的排查论证、自我对话——
这些是产结论的工序，**只有改变结论的产出进文件**，过程留在对话或流水账里。

**判据一句**：删掉这段，拍板的人会误判、或后续步骤会取错值吗？不会就删；
某节全流程无人消费，直接不产。

> **过程账淹结论，是所有产物膨胀病的最大宗。**

## 适用面

**给人读的文字**：需求正文 / 页面规格 / 方案概述 / 原型页面说明 / 对话汇报。
**不适用**：操作流水、抓取产物、脚本与 JSON——它们的读者是机器或审计，完整性优先于精简。
