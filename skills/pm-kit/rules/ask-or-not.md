# 该不该问：决策分流协议

> **何时读**：任何时候你即将产生一条「需要人拍板 / 确认 / 待定」的事项——写进待确认表之前、
> 弹窗问之前、汇报里列出来之前。**先过本文件定"该不该问"，再按 `stop-report.md` 定"什么时候问、怎么摆"。**
>
> **为什么它排在所有规则前面**：技术类问题一旦被摆进给需求负责人的决策列表，他答不了、
> 只会说"我不懂"，那个决策就 100% 由 AI 代决了——而且是在所有人都以为"已经确认过"的情况下代决的。

## 总判据（先过它，再分档）

把两三个候选答案分别代入，问一句：

> **他在界面上、在业务规则上看得出差别吗？**

- **看得出** → 这是业务问题，可能该问（继续往下分档）。
- **看不出** → 实现问题，到此为止：不问、不标、不写进任何产物。

**不要用"他听不听得懂"当判据。** 听得懂的技术题他就会答，答完还得自己声明"我这回答有点越界"——
听得懂是他的能力，不是该问他的理由。

## 判断树（每条候选逐条过，命中即止）

```
这条事项 →
⓪ 本单他已经答过了？          ─ 是 → 采用他的答案 + 留痕，不再问
① 项目既有事实 / 系统设计常识能回答？ ─ 能 → 先自答，不进决策列表
② 看得出差别（界面或业务规则会不同）？ ─ 是 → 过「先自答三格」，填得出第三格才升为待拍板
   ↳ 进了再分一岔：这条谁答？  他 → 🔴 待拍板 ｜ 外部客户 → ⏳ 待客户 ｜ 我方自己 → ℹ️ 我方内部
③ 看不出差别，但影响成本 / 跨系统契约？ ─ 是 → 只落文末技术附录的「研发开工自查项」，
                                        不问、不进汇报、不进待确认表
④ 看不出差别，研发换任一写法都满足？   ─ 是 → 不产生、不记录、不汇报
```

## 先自答三格（②档准入，写成问句之前先填）

| 格 | 填什么 | 填不出意味着 |
|---|---|---|
| **我的答案** | 一句话给出判断，**不许写"不确定"** | 才是真空白，继续往下 |
| **依据** | 四选一：① 他已答过 ② 项目既有事实 ③ **系统设计常识** ④ 客户材料明说 | 四项都不沾 → 确实需要外部输入 |
| **另一种合理答案** | 它是什么、**谁会选它、为什么** | **没有分歧 = 不问**，按"我的答案"直接写，汇报里一行知悉即可 |

三格都填得出、且第二种答案真有人会选 → 才升 🔴。

反例（三格全不成立，所以都不该问）：

| 问了什么 | 我的答案 | 另一种合理答案 | 结果 |
|---|---|---|---|
| 「有没有撤回操作？文档只写了发布」 | 有（发布↔撤回是对偶） | "没有撤回"——谁会选？ | 填不出 → **不问，直接补上** |
| 「选『我创建的』反而看不见别人的，这个语义倒挂接受吗？」 | 就该只看自己的（筛选的本义） | 没人会选 | 填不出 → **不问** |
| 「普通管理员改造后该看到什么？」 | 不变，只动两个超管账号 | — | 依据①命中 → **不问** |

> **为什么做成填格而不是又一条判断规则**：规则要靠"记得想起来"，格子是**写的动作本身**——
> 被迫先写下"我的答案：有撤回，因为发布/撤回是对偶"，写到这儿问句就自然产生不出来了。

## 系统设计常识：是默认值，不是未决点

**常识 = 同行产品普遍这么做、反过来做会被当成缺陷的那一类。**
发布↔撤回、启用↔停用、创建↔删除、绑定↔解绑、导入↔导出；筛选器缩小结果集；分页有总数；删除要二次确认。

- **常识缺项 → 自己补进规格**，汇报里一行「按对偶补了 X，不需要请指出」（供知悉，不占拍板位）。
  他要否决很便宜，一句话的事；而问他一次，花的是他对整份产出的信任。
- **文档里查不到 ≠ 推翻常识**。"文档只写了发布"只说明文档没写全，不说明产品没有撤回。
  按常识写 + 标一行诚实边界即可。
- **例外**：补了会显著扩范围、客户明确排除过、或删除策略这类必须定口径的 → 回三格走②档。

## 说"矛盾 / 不一致"之前，先验它成不成立

**成立标准：用户在同一时刻同时期待两件事，而系统只能满足一件。**

- ❌ 不成立：「选了『我创建的』就看不见别人的 = 语义倒挂」——用户选它就是在表达"只要我的"，
  他不会同时期待看到别人的。
- ✅ 成立：概览写「前端零调整」，页面规格却要求加载态换显示——两条同时成立不了，必须消解。

自检一句：**把这条"矛盾"讲给一个不懂本需求的同行听，他会不会回一句"本来就该这样"？**
会 → 不是矛盾，是我还没想通，回去想通它。

## 混装必拆

一条里既有产品成分又有实现成分 → 拆开各按档处理。
典型：「新的获得方式取值取几（产品）+ 关联表怎么存（研发）」——拆开后产品那半往往早有答案，
**整条根本不用问**。

## ②档上浮的必须是业务规则形态，不许是实现选项列表

- ❌ 「不含测评时那两个必填字段怎么落：传空占位 / 改列可空 / 哨兵值？」
- ✅ 「**不含测评的证书，还要不要填评估方案和指标匹配率？** 现在这两项是必填。
     建议：选『只看培训项目』口径时这两项直接隐藏、不参与校验；备选：仍要求填但允许留空。」

**自检**：候选项里出现「传空 / 改列 / 哨兵值 / 字段 / 接口 / 枚举值 / 关联表」这类词
= 还没还原成业务问法，回去重写。

## 问错问题的代价不是零

问一个常识题，花掉的不是他十秒钟，是他对整份产出的信任。
所以"拿不准就问一下更安全"**不是**安全策略——它把不确定性的成本转嫁给了别人对你的信任。
**不确定时的正确动作是先自答，不是先提问。**

## 反向那一半：查到疑点 ≠ 必须让人回答

在实现层看到不确定、不一致、多个可选实现时，第一反应不是"该问谁"，
而是先问"**需求阶段需要这条有答案吗**"——不需要就到此为止。

**它甚至不该被查出来**：见 `evidence.md`「查证前先过收益问」——
技术疑问不仅不问、不标、不写，**也不为它去查**。工具就在手边、查起来很容易，都不是理由。
